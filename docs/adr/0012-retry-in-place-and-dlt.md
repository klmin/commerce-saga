# ADR 0012. 실패 처리: 일시 오류는 제자리 재시도, 영구 오류는 DLT + 재처리 도구. 지연 retry 토픽은 쓰지 않는다

- 상태: 채택
- 날짜: 2026-11-22

## 배경

컨슈머가 메시지를 처리하다 실패하는 경우는 두 가지다.

- **일시 오류**: DB 연결 끊김, 락 타임아웃, 브로커 일시 장애. 기다리면 같은 메시지가 성공한다
- **영구 오류**: 깨진 JSON, `type`·`id` 헤더 없음, 계약에 없는 타입, 데이터 불일치(예약한 상품이 사라짐). 몇 번을 다시 해도 같다

브리프는 "retry 토픽 → DLQ"였다. Spring Kafka의 `@RetryableTopic`은 실패한 메시지를 `<토픽>-retry-1s`, `-retry-10s` 같은 지연 토픽으로 옮겨 나중에 다시 처리하고, 끝까지 실패하면 DLT로 보낸다. 원래 파티션은 막히지 않고 다음 메시지로 넘어간다.

## 결정

| 오류 | 처리 | 파티션 |
|---|---|---|
| 일시 오류 (아래 목록 외 모든 예외) | **같은 자리에서** 지수 백오프로 재시도 (0.5초, 2배씩, 최대 30초 간격, 횟수 무제한). 복구되면 이어서 처리 | 그 파티션은 복구될 때까지 멈춘다 |
| 영구 오류 (`JacksonException`, `NonRetryableMessageException`, `InvariantViolationException`) | 재시도 없이 원본을 `<토픽>.DLT`로 옮기고 다음 메시지로 | 막히지 않는다 |
| DLT에 쌓인 메시지 | 원인을 고친 뒤 `scripts/dlt.sh`로 조회·재처리 | — |

구현은 서비스마다 `common/config/KafkaErrorHandlingConfig`(`DefaultErrorHandler` + `DeadLetterPublishingRecoverer`), 재처리 도구는 `tools/dlt-replay`.

### 지연 retry 토픽을 쓰지 않는 이유: 주문 단위 순서

이 시스템은 메시지 키 = `orderId`로 **같은 주문의 메시지 순서**에 기대고 있다 (ADR 0005). retry 토픽으로 한 메시지를 빼내면 같은 주문의 뒤 메시지가 먼저 처리된다.

```
inventory.command 파티션 1:  ReserveStock(A)  →  ReleaseStock(A)
                              │ DB 일시 오류
                              └─> retry-10s 토픽으로 빠짐
                                               ReleaseStock(A) 먼저 처리: 예약 없음 → 해제 기록(tombstone)
              10초 뒤 ReserveStock(A) 재처리: 해제 기록이 있어 거절
```

보상 계약(앞 단계 없이 온 보상도 안전, ADR 0003) 덕에 이 경우 재고가 새지는 않는다. 하지만 정방향 단계에서는 이야기가 다르다. `UsePoint` 다음 `Pay`처럼 앞 메시지가 처리됐다는 전제로 다음 메시지를 보내는 흐름은 순서가 바뀌면 상태 머신이 기대하지 않은 응답 순서를 받게 된다. 모든 조합에서 안전한지 증명하는 것보다 순서를 지키는 쪽이 단순하다.

일시 오류는 대개 그 서비스의 DB나 브로커 문제라, 한 메시지만이 아니라 **같은 파티션의 다음 메시지도 똑같이 실패**한다. retry 토픽으로 넘겨도 다음 메시지가 또 retry 토픽으로 갈 뿐 실제로 처리량이 나아지지 않는다. 그래서 제자리에서 기다리는 비용이 크지 않다.

### 재처리 도구 (`tools/dlt-replay`, `scripts/dlt.sh`)

- `list <토픽>.DLT`: 메시지마다 key, type, id, 원래 위치(토픽/파티션@오프셋), 실패 원인(예외 클래스·메시지), 본문
- `replay <토픽>.DLT --offset P:O[,...] | --all [--dry-run]`: 원래 토픽으로 다시 보낸다. key·value·원본 헤더는 그대로, `kafka_dlt-*` 헤더만 빼고 `x-dlt-replayed-from`(출처)을 붙인다
- **메시지 `id`를 바꾸지 않는다.** 이미 처리된 메시지가 섞여 있거나 같은 것을 두 번 재처리해도 컨슈머의 `processed_message`가 한 번만 반영한다 (ADR 0006). 그래서 도구는 "어디까지 재처리했는지"를 기억하지 않아도 된다
- 컨슈머 그룹 없이 파티션을 직접 읽어 서비스 오프셋에 영향이 없다. Kafka는 메시지를 골라 지울 수 없어 재처리한 메시지도 DLT에 남는다
- 서비스가 아니라 사람이 장애 복구 때 쓰는 CLI라 Spring 없이 `kafka-clients`만 쓴다. 관리 API를 서비스마다 넣는 방식은 같은 코드가 다섯 벌이 되고, 공개 API 표면이 늘어서 택하지 않았다

### 재처리할 때 주의

- 원인을 고치지 않고 재처리하면 같은 이유로 DLT에 다시 온다 (해롭지는 않다)
- 오래된 커맨드를 재처리하면 Saga가 이미 다른 단계에 있을 수 있다. 참여 서비스는 주문별 기록으로, 오케스트레이터는 상태 머신으로 늦은 메시지를 걸러 상태를 되돌리지 않는다. 예: `ReserveStock`이 DLT에 있는 동안 Saga가 보상(`ReleaseStock`)까지 끝났으면, 재처리한 `ReserveStock`은 해제 기록 때문에 거절된다
- 응답 토픽(`*.reply.DLT`)을 재처리하면 오케스트레이터가 받는다. 현재 단계와 맞지 않으면 무시된다

## 결과

- 좋은 점: 주문 단위 순서가 어떤 실패에서도 유지된다. 영구 오류는 원본·원인과 함께 보존되고 사람이 확인한 뒤 재처리할 수 있다 (시나리오 6)
- 비용: 일시 오류 동안 그 파티션의 처리가 멈춘다. 다른 파티션(다른 주문)은 계속 처리된다
- 위험: 영구 오류인데 목록에 없는 예외(예: 코드 버그로 인한 `NullPointerException`)는 일시 오류로 분류되어 **그 파티션을 계속 막는다.** 메시지를 건너뛰어 주문 하나의 정합성을 깨는 것보다, 멈추고 고치는 쪽을 택했다. 대신 빨리 알아채야 하므로 컨슈머 lag과 같은 오류 반복 로그를 감시한다 (후속 관측성 작업에서 경보로 붙인다). 이런 예외가 확인되면 `NonRetryableMessageException`으로 분류를 고친다
- 다시 검토할 때: 같은 주문 안의 순서가 필요 없는 토픽(예: 알림처럼 사실만 기록하는 소비자)이 늘거나, 외부 API 호출처럼 한 메시지만 오래 실패하는 경우가 생기면 그 토픽에 한해 retry 토픽을 쓴다
