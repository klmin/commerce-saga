# ADR 0016. 주문 가격: product-service 를 동기 조회하고 화면 가격과 다르면 409

- 상태: 채택
- 날짜: 2026-11-25

## 배경

지금은 클라이언트가 주문 요청에 `unitPrice` 를 보내고 서버가 그대로 믿는다(F-1b 결정 (a), PROGRESS 5절 한계). 가격을 가진 서비스가 없고 프론트 고정 목록(`frontend/src/lib/products.ts`)이 가격의 출처다. 후속 4-1 에서 서버가 가격을 정하게 한다.

AGENTS.md 는 서비스 간 **조회**에 "이벤트로 받은 읽기 모델 우선, 동기 조회는 ADR 로 이유를 남긴 예외(타임아웃·fallback), Saga 리스너 안에서는 금지"를 둔다(PR #63). 이 ADR 이 그 예외다.

## 고려한 안

| | A. 주문 요청 때 동기 조회 | B. 가격 이벤트 → order 읽기 모델 |
|---|---|---|
| 얻는 값 | product 가 지금 가진 가격 | 마지막으로 받은 가격 (이벤트 지연만큼 늦음) |
| product 장애 | 주문 생성 실패(503). 이미 진행 중인 Saga 는 영향 없음 | 주문은 되지만 옛 가격일 수 있음 |
| 추가 구성 | HTTP 클라이언트(타임아웃) | `product.events` 토픽·스키마, order 쪽 컨슈머·테이블·멱등, 처음 채우기(백필) |
| 가격 변경 직후 | 바로 새 가격 | 지연 동안 옛 가격으로 주문 가능 |

- 가격은 **주문을 만드는 그 순간 한 번** 필요하고, 실시간 값이어야 한다(관리자가 바꾼 직후의 주문이 옛 가격이면 안 됨). AGENTS.md 의 "실시간 값이 꼭 필요할 때"에 해당한다
- 조회는 product DB 의 기본 키 조회 몇 건이라 가볍고, **상태를 바꾸지 않으므로** ADR 0000 이 막는 "동기 HTTP 로 다른 서비스 상태 변경"이 아니다
- 이 조회는 주문 API 요청 안에서만 일어나고 Saga 단계와 무관하다. product 가 멈춰도 새 주문만 막히고, 진행 중인 Saga·보상은 그대로 돈다(장애 격리 유지)
- B 는 정합성 문제(이벤트 지연 동안 옛 가격)를 새로 만들고, 그것을 해결하려면 결국 주문 시점에 확인이 필요하다. 읽기 모델은 화면 목록처럼 대량·반복 조회가 있을 때 의미가 있고, 그건 product 가 직접 서빙한다(검색은 ④ ES)

## 결정

1. **product-service** 를 새로 만든다. 상품·가격의 주인이고, 가격을 바꾸면 같은 트랜잭션에 변경 이력(이전 가격·새 가격·바꾼 사람·시각)을 남긴다(ADR 0015 에서 미룬 audit 을 도메인 이력으로)
2. order-service 는 주문 생성 때 product-service 의 조회 API(`GET /products?ids=…`)를 **한 번에 여러 상품** 동기 호출한다
   - `adapter.out` 의 포트 구현, **DB 트랜잭션 밖**(조회 → 검증 → 트랜잭션 시작 순서)
   - 연결·응답 타임아웃 2초, 재시도 없음. 실패·타임아웃이면 주문을 만들지 않고 503(Problem Details). 상태를 바꾸지 않는 조회라 "결과 모름"이 없다
   - **Saga 리스너·스케줄러에서는 부르지 않는다.** 가격은 주문 행의 스냅샷(`order_lines.unit_price`)만 쓴다
3. 요청 DTO 의 `unitPrice` 는 이름을 유지하되 의미를 **"화면에서 본 가격(기대 가격)"** 으로 바꾼다. 서버 가격과 하나라도 다르면(오르든 내리든) **409** + 줄별 현재 가격을 돌려주고 주문을 만들지 않는다. 사용자가 확인하면 새 가격으로 다시 요청한다. 같으면 서버 가격을 주문에 스냅샷한다. 없는 상품·판매 중지 상품은 422
4. 409·503·422 일 때는 `Idempotency-Key` 를 기록하지 않는다(같은 키로 다시 보낼 수 있어야 함). 같은 키로 다른 가격을 보내면 지금처럼 키 재사용 오류(요청 해시가 다름)
5. 메시지 계약은 바꾸지 않는다. 금액은 지금처럼 주문 행에서 계산해 커맨드에 싣는다
6. 상품 목록·상세·여러 건 조회는 로그인 없이 볼 수 있는 공개 조회다(카탈로그). order 는 Gateway 를 거치지 않고 클러스터 안에서 product 의 같은 조회 API(`GET /products?ids=…`)를 부른다. 토큰을 전달하지 않는다. 쓰기(등록·가격 변경)는 ADMIN 만

### 장바구니 (같은 4-1)

- **order-service** 안에 둔다. 장바구니는 주문 전 단계라 주문 컨텍스트이고, 장바구니로 주문할 때 **주문 생성과 주문한 줄 삭제를 한 트랜잭션**으로 묶을 수 있다(별도 서비스면 이 둘이 또 분산 정합성 문제가 된다)
- 저장은 order DB(Postgres). 사용자별 몇 줄이라 충분하고, Redis 용도를 늘리지 않는다(브리프는 Redis 를 refresh token·rate limit 으로 제한)
- 줄마다 상품 id·수량·**담을 때 본 가격**. 조회 때 product 에서 현재 가격을 한 번에 받아 "담은 뒤 가격이 바뀜"을 표시한다. product 가 응답하지 않으면 장바구니는 담을 때 가격으로 보여 주고 표시만 뺀다(조회 fallback)
- 장바구니 주문도 위 3번과 같다: 화면 가격을 보내고 다르면 409
- 소유권은 JWT `sub`. 장바구니 id 를 받지 않고 "내 장바구니"만 있다. 최대 50줄(주문 최대 줄 수와 같음)

## 결과와 위험

- 좋은 점: 주문 금액을 서버가 정한다. 화면과 다르면 사용자가 확인한 뒤에만 주문된다(일반적인 커머스의 결제 직전 재확인과 같은 흐름)
- 비용: product 가 멈추면 **새 주문**이 막힌다(503). 진행 중인 Saga 에는 영향이 없다. 주문 API 지연에 product 조회 시간이 더해진다
- 위험: 409 가 반복되면(가격이 자주 바뀜) 사용자가 주문을 못 할 수 있다 → 관리자 가격 변경 빈도가 낮다는 가정. 문제가 되면 "가격이 내리면 그대로 진행"으로 완화할 수 있다
- 다시 검토할 때: 화면 외 다른 소비자(정산·통계)가 가격 변경을 알아야 하면 `product.events` 를 추가한다(그때도 주문 시점 확인은 동기 조회 유지)
