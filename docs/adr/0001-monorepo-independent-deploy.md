# ADR 0001. 모노레포 + 서비스별 독립 실행·배포

- 상태: 채택
- 날짜: 2026-11-22

## 배경

서비스가 5개(1~3단계)에서 9개(6단계)까지 늘어난다. 저장소를 서비스마다 나눌지, 하나로 둘지 정해야 한다.

MSA에서 얻으려는 것은 독립 배포·독립 확장·장애 격리다. 이것을 결정하는 것은 저장소 개수가 아니라 **배포 단위와 데이터 소유권**이다.

## 결정

Gradle 멀티모듈 모노레포 하나에 두되, 서비스는 각자 독립 실행·배포되는 Spring Boot 앱으로 만든다.

- `services/*`: 서비스마다 자기 jar(이미지), 자기 DB, 자기 Flyway 마이그레이션
- `libs/messaging-contract`: 메시지 스키마만. `libs/outbox`: outbox 인프라만
- `build-logic`: 공통 빌드 설정(convention plugin). 의존성 버전을 한 곳에서 맞춘다

경계를 지키는 장치:

| 위반 | 막는 방법 |
|---|---|
| 다른 서비스 DB 접근 | 서비스마다 DB·계정 분리. `public` 접속 권한 회수 (`infra/postgres/init`), CI(`infra.yml`)에서 교차 접속이 실패하는지 확인 |
| 서비스 간 코드 공유 | `services/*` 사이 의존 금지 (AGENTS.md 리뷰 규칙). 공유는 libs 두 개까지 |
| 동기 호출 결합 | 서비스 간 통신은 Kafka 메시지만 |
| 모든 서비스 동시 빌드 | CI(`backend.yml`) 경로 필터로 바뀐 서비스만 빌드. libs·빌드 설정이 바뀔 때만 전체 |

## 결과

- 좋은 점: 메시지 계약을 바꿀 때 생산자·소비자를 한 PR에서 같이 고치고 검증할 수 있다. 버전·빌드 설정이 흩어지지 않는다. 포트폴리오로 한 저장소에서 전체 흐름을 보여줄 수 있다
- 나쁜 점: 경계가 컴파일러로 강제되지 않고 규칙·리뷰에 기댄다. libs 변경은 모든 서비스 재빌드를 부른다
- 서비스를 다른 팀이 소유하게 되면 그때 저장소를 나눈다. 그 전까지는 계약 변경 비용이 낮은 쪽을 택한다
