# ADR 0007. Saga 타임아웃과 결제 타임아웃 보정: 재전송 후 포기하면 역순 보상, 결제는 PG 조회로 확정하고 늦은 승인은 자동 환불

- 상태: 채택 (3-D-1 멈춘 Saga 정리 PR #24, 3-D-2 결제 타임아웃 보정에서 결제 부분을 덧붙임)
- 날짜: 2026-11-23

## 배경

주문 Saga는 단계마다 커맨드를 보내고 응답을 기다린다(ADR 0003). 응답이 영영 오지 않으면 Saga가 그 단계에 멈춘다.

- 참여 서비스가 오래 다운됨 (커맨드는 Kafka에 쌓여 있음)
- 커맨드나 응답이 처리 불가로 DLT에 감 (ADR 0012)
- 결제처럼 결과가 애매함 (PG 타임아웃, 승인됐을 수 있음)

지금까지는 이런 Saga가 `PENDING`으로 계속 남았다. 재고는 예약된 채, 포인트는 차감된 채로 남을 수 있다.

## 결정

order-service에 **단계 타임아웃**을 둔다 (`saga.timeout.*`). 스케줄러가 주기적으로(`scan-interval`, 기본 5초) "끝나지 않았고 `step-timeout`(기본 30초) 동안 바뀌지 않은" Saga를 찾아 단계마다 정해진 일을 한다. 판단은 도메인(`OrderSaga.onTimeout`)이 한다.

| 멈춘 단계 | 타임아웃마다 | `max-resends`(기본 3)를 넘으면 |
|---|---|---|
| `RESERVING_STOCK` | `ReserveStock` 재전송 | 포기 → `RELEASING_STOCK` (`ReleaseStock`) |
| `USING_POINT` | `UsePoint` 재전송 | 포기 → `REFUNDING_POINT` (`RefundPoint`) → 재고 해제 |
| `PAYING` | `Pay` 재전송 (결제 서비스가 PG 조회로 확정한 결과를 응답) | `max-payment-resends`(기본 10)를 넘으면 포기 → `CANCELLING_PAYMENT` (`CancelPayment`) → 포인트 환불 → 재고 해제. 늦게 승인되면 결제 서비스가 환불 |
| `CANCELLING_PAYMENT`, `REFUNDING_POINT`, `RELEASING_STOCK` (보상) | 같은 보상 커맨드 재전송 | **포기하지 않는다**. 오래 걸리면 경고 로그 |

### 재전송은 "다시 묻기"다

재전송은 **새 메시지 id**로 나간다. 같은 id면 참여 서비스가 `processed_message`로 건너뛰어 응답도 하지 않기 때문이다. 참여 서비스는 내용이 같은 재요청을 주문별 기록(예약·사용·결제, `order_id` 유니크)으로 걸러 **상태는 그대로 두고 처음 결과를 다시 응답**한다(ADR 0006). 그래서 재전송은 몇 번이 되든 한 번만 반영되고, 응답이 유실됐거나 DLT로 갔던 경우에는 Saga를 다시 움직인다. 처음 응답과 재전송에 대한 응답이 둘 다 오면 뒤의 것은 상태 머신이 무시한다.

### 포기하면 "반영됐다고 보고" 보상한다

재고 예약이나 포인트 차감은 응답이 없으면 반영됐는지 알 수 없다. 그래서 **반영됐다고 보고** 그 단계부터 역순 보상한다. 포인트 차감에서 포기하면 `pointUsed`가 false여도 환불부터 보낸다. 이것이 안전한 이유는 두 가지다.

1. 보상 커맨드는 앞 단계가 없었어도 안전하다. inventory는 예약 없이 해제가 오면 "해제됨" 기록을, point는 사용 없이 환불이 오면 "환불됨" 기록을 남겨 늦게 온 예약·차감을 막고, 둘 다 항상 성공 응답을 보낸다
2. 같은 주문의 커맨드는 키가 같아 **보낸 순서대로** 처리된다(ADR 0005). 참여 서비스가 나중에 살아나도 밀린 `UsePoint`가 먼저, `RefundPoint`가 나중에 처리되어 결과는 "차감 후 환불"이다 (시나리오 4b)

포기한 뒤 늦게 온 성공 응답(`PointUsed`, `StockReserved`)은 현재 단계가 기다리는 응답이 아니라 무시한다. 단계가 되돌아가지 않는다.

### 결제는 바로 보상하지 않는다: PG 조회로 확정하고, 오래 걸리면 결제 취소 + 늦은 승인 자동 환불 (3-D-2)

결제는 "응답 없음"이 "돈이 안 나갔음"을 뜻하지 않는다. PG 응답이 늦거나, PG가 승인했는데 결제 서비스가 기록 전에 죽을 수 있다. 여기서 바로 보상하면 **돈은 나갔는데 주문은 취소**된다. 그래서 두 서비스가 나눠 맡는다.

**payment-service: PG 타임아웃은 실패가 아니라 "모름"이다**
- PG 호출에 클라이언트 타임아웃(`fake-pg.client-timeout`, 기본 3초)을 둔다. 넘으면 결제를 `UNKNOWN`으로 기록하고 **응답하지 않는다**(실패로 응답하면 Saga가 보상해 버린다)
- 결제 보정 작업(`payment.reconcile.*`, 기본 2초 주기)이 `UNKNOWN`을 **PG 조회**로 확정한다. 승인·거절이 나오면 그때 기록하고 응답한다. 조회에 거래가 `not-found-after`(기본 2분, PG 최대 처리 시간보다 길게) 동안 계속 없으면 PG가 요청을 받지 못한 것으로 보고 거절로 확정한다
- 그사이 Saga가 `Pay`를 다시 보내도 `UNKNOWN`이면 PG를 다시 부르지 않고 응답도 하지 않는다(확정될 때 한 번 응답)

**order-service: 결제는 더 오래 묻고, 그래도 안 되면 결제 취소부터**
- `PAYING`은 `max-payment-resends`(기본 10, 30초 × 11 ≈ 5.5분)까지 `Pay`를 다시 보낸다. 재고·포인트(3번)보다 길게 기다린다
- 넘으면 포기하고 새 상태 `CANCELLING_PAYMENT`에서 **`CancelPayment`**를 보낸다(새 커맨드, 응답 `PaymentCancelled`). 결제 취소도 보상이라 응답이 올 때까지 계속 다시 보낸다
- `PaymentCancelled`를 받으면 나머지를 역순으로 되돌린다(포인트를 썼으면 환불 → 재고 해제 → `CANCELLED`). 실패 사유는 결제 타임아웃 그대로 남는다. 취소를 보낸 뒤 늦게 온 `PaymentApproved`·`PaymentFailed`는 무시한다

**payment-service: 취소는 접수하고, 환불은 끝까지 책임진다**
- `CancelPayment`는 PG를 부르지 않고 결제에 **취소 요청**을 기록한 뒤 바로 `PaymentCancelled`로 응답한다(결제 행 잠금 + 처리 기록 + 응답 outbox = 한 트랜잭션). Saga는 환불이 끝나기를 기다리지 않는다
- 결제 기록이 없으면(Pay가 아직 처리 안 됐거나 DLT로 감) `CANCELLED` 기록을 남긴다. 나중에 그 주문의 `Pay`가 와도 PG를 부르지 않고 실패로 응답한다(inventory·point의 "해제됨/환불됨" 기록과 같은 방식)
- 결제 보정 작업이 "취소 요청 + 승인" 상태를 찾아 **PG 환불** 후 `REFUNDED`로 바꾼다. 이미 승인된 결제를 취소한 경우도, `UNKNOWN`에서 취소 요청을 받은 뒤 PG 조회로 **늦게 승인이 확인된** 경우도 같은 길이다(늦은 승인 자동 환불). 이때 승인 응답은 보내지 않는다(Saga는 이미 보상 중)
- PG 호출(조회·환불)은 트랜잭션 밖에서 하고, 결과 반영은 결제 행을 잠근 트랜잭션에서 상태를 다시 보고 한다. 응답·환불이 두 번 일어나지 않고, PG 환불 자체도 주문별로 멱등이다

**가짜 PG**: 승인 처리를 PG 쪽 스레드에서 돌려, 클라이언트가 타임아웃으로 포기해도 PG는 계속 처리해 나중에 승인한다(`DELAY` 모드). 조회(`inquire`)·환불(`refund`, 원장 `refunded`)을 추가했다. 실제 PG처럼 결제 서비스가 재시작되면 처리 중이던 요청은 사라진다(원장에 없음 → `not-found-after` 뒤 거절 확정).

**배포 순서**: `PaymentCancelled`를 받는 order-service를 먼저 배포한다. payment.reply는 계약에 없는 타입을 DLT로 보내기 때문이다. `CancelPayment`는 새 order-service만 보내므로 payment-service가 나중이어도 그동안 payment.command에 들어올 일이 없다(포기까지 몇 분 걸림). 그래도 순서가 바뀌면 DLT에 남고 `scripts/dlt.sh`로 재처리할 수 있다.

### 보상은 끝까지 다시 보낸다

보상을 포기하면 재고·포인트가 묶인 채 남는다. 보상 커맨드는 멱등이라 몇 번 보내도 안전하므로 성공할 때까지 `step-timeout` 간격으로 다시 보낸다. 재전송 횟수가 `max-resends`를 넘으면 경고 로그를 남긴다(경보는 후속 관측성 작업).

### 동시성

- 응답 처리와 타임아웃 처리는 같은 Saga 행 락(`SELECT … FOR UPDATE`)을 잡는다. 겹쳐도 하나씩 처리된다
- 스캔은 잠그지 않고 id만 읽는다. Saga마다 따로 트랜잭션에서 잠근 뒤 `updatedAt`으로 **다시 판단**한다. 그사이 응답이 와서 진행됐거나 다른 인스턴스가 방금 재전송했으면 아무것도 하지 않는다. 그래서 order-service를 여러 개 띄워도 같은 Saga를 두 번 처리하지 않는다
- Saga 변경 + 재전송 커맨드 outbox 저장 = 한 트랜잭션 (원자성은 응답 처리와 같음)
- 스캔 쿼리는 진행 중 Saga만 담은 부분 인덱스(`idx_order_sagas_in_progress_updated_at`)를 쓴다. 끝난 Saga는 계속 쌓이므로 인덱스에서 뺐다

### 값 정하기

- `step-timeout`은 정상 응답 시간(수백 ms ~ 1초, 시나리오 7)보다 충분히 길어야 한다. 짧으면 정상 Saga에 불필요한 재전송이 나간다(결과는 같지만 부하)
- `step-timeout × (max-resends + 1)`은 **참여 서비스가 죽었다 살아나는 시간보다 길어야** 한다. 짧으면 복구될 장애도 보상으로 끝난다. 프로세스가 죽으면 Kafka가 그 컨슈머를 `session.timeout.ms`(기본 45초) 뒤에야 그룹에서 빼므로, 재기동 시간 + 45초가 하한이다 (시나리오 4에서 발견). 기본값 30초 × 4 = 2분
- 결제는 재전송 횟수만 따로(`max-payment-resends`) 두어 더 오래 기다린다. `step-timeout × (max-payment-resends + 1)`은 PG 최대 처리 시간보다 길게 두는 것이 좋다(짧으면 늦은 승인 → 환불이 늘어난다). 결제 서비스의 `not-found-after`도 PG 최대 처리 시간보다 길어야 한다(짧으면 늦게 승인될 거래를 거절로 확정해 버린다)

## 대안

- **Saga마다 데드라인 시각을 저장**(`deadline_at`): 단계마다 다른 시간을 두기 쉽다. 지금은 `updatedAt` + 공통 타임아웃으로 충분하고 컬럼·인덱스가 하나 덜 든다
- **지연 메시지(타이머 토픽)로 타임아웃 이벤트 예약**: 스캔이 없지만, Kafka에는 지연 전달이 없어 별도 토픽·소비자가 필요하고 같은 주문의 순서 보장과 섞인다(ADR 0012에서 retry 토픽을 안 쓴 이유와 같음)
- **재전송 없이 바로 보상**: 일시적인 응답 유실(DLT)에도 주문이 취소된다. 재전송은 멱등이라 비용이 거의 없다
- **워크플로 엔진(Temporal 등)의 타이머**: 3-E ADR 0000에서 비교한다
- **결제 타임아웃이면 바로 실패 응답 + PG 망취소(즉시 취소 요청)**: PG 대부분이 지원하는 방식이다. 하지만 망취소 요청 자체도 타임아웃날 수 있어 결국 조회·재시도가 필요하고, 그동안 Saga가 실패로 보상해 버리면 승인된 돈이 남는다. 조회로 확정하는 쪽이 상태가 더 단순하다
- **결제 단계는 끝까지 기다림(포기 없음, 3-D-1의 동작)**: 결제 서비스나 PG가 오래 다운되면 재고·포인트가 계속 묶인다

## 결과

- 좋은 점: 응답이 오지 않아도 Saga가 끝난다(완료 또는 취소). 일시 장애는 재전송으로 이어서 완료, 긴 장애는 역순 보상으로 재고·포인트가 풀린다. 결제는 애매한 상태에서 섣불리 보상하지 않고 PG 조회로 확정한다. 결제를 포기하고 취소한 뒤 PG가 늦게 승인해도 자동 환불되어 돈이 남지 않는다 (시나리오 2)
- 비용: order-service가 주기적으로 진행 중 Saga를 조회한다(기본 5초에 한 번, 인덱스 조회). 재전송만큼 참여 서비스가 중복 응답을 보낸다
- 비용(결제): 결제 서비스가 주기적으로 보정 대상(부분 인덱스)을 조회한다. 결제 취소 응답과 실제 환불 사이에 시간 차가 있다(주문은 취소, 환불은 몇 초~몇 분 뒤)
- 한계: 환불이 계속 실패하면(PG 장애) 끝없이 재시도하고 경고 로그만 남긴다. 결제 상태 `UNKNOWN`·환불 대기 건수 경보는 후속 관측성 작업
