# ADR 0007. Saga 타임아웃: 재전송 후 포기하면 역순 보상, 결제는 포기하지 않고 다시 묻는다

- 상태: 채택 (멈춘 Saga 정리. 결제 쪽 PG 조회·늦은 승인 환불은 3-D-2에서 이 ADR에 덧붙인다)
- 날짜: 2026-11-23

## 배경

주문 Saga는 단계마다 커맨드를 보내고 응답을 기다린다(ADR 0003). 응답이 영영 오지 않으면 Saga가 그 단계에 멈춘다.

- 참여 서비스가 오래 다운됨 (커맨드는 Kafka에 쌓여 있음)
- 커맨드나 응답이 처리 불가로 DLT에 감 (ADR 0012)
- 결제처럼 결과가 애매함 (PG 타임아웃, 승인됐을 수 있음)

지금까지는 이런 Saga가 `PENDING`으로 계속 남았다. 재고는 예약된 채, 포인트는 차감된 채로 남을 수 있다.

## 결정

order-service에 **단계 타임아웃**을 둔다 (`saga.timeout.*`). 스케줄러가 주기적으로(`scan-interval`, 기본 5초) "끝나지 않았고 `step-timeout`(기본 30초) 동안 바뀌지 않은" Saga를 찾아 단계마다 정해진 일을 한다. 판단은 도메인(`OrderSaga.onTimeout`)이 한다.

| 멈춘 단계 | 타임아웃마다 | `max-resends`(기본 3)를 넘으면 |
|---|---|---|
| `RESERVING_STOCK` | `ReserveStock` 재전송 | 포기 → `RELEASING_STOCK` (`ReleaseStock`) |
| `USING_POINT` | `UsePoint` 재전송 | 포기 → `REFUNDING_POINT` (`RefundPoint`) → 재고 해제 |
| `PAYING` | `Pay` 재전송 | **포기하지 않는다**. 계속 다시 묻는다 |
| `REFUNDING_POINT`, `RELEASING_STOCK` (보상) | 같은 보상 커맨드 재전송 | **포기하지 않는다**. 오래 걸리면 경고 로그 |

### 재전송은 "다시 묻기"다

재전송은 **새 메시지 id**로 나간다. 같은 id면 참여 서비스가 `processed_message`로 건너뛰어 응답도 하지 않기 때문이다. 참여 서비스는 내용이 같은 재요청을 주문별 기록(예약·사용·결제, `order_id` 유니크)으로 걸러 **상태는 그대로 두고 처음 결과를 다시 응답**한다(ADR 0006). 그래서 재전송은 몇 번이 되든 한 번만 반영되고, 응답이 유실됐거나 DLT로 갔던 경우에는 Saga를 다시 움직인다. 처음 응답과 재전송에 대한 응답이 둘 다 오면 뒤의 것은 상태 머신이 무시한다.

### 포기하면 "반영됐다고 보고" 보상한다

재고 예약이나 포인트 차감은 응답이 없으면 반영됐는지 알 수 없다. 그래서 **반영됐다고 보고** 그 단계부터 역순 보상한다. 포인트 차감에서 포기하면 `pointUsed`가 false여도 환불부터 보낸다. 이것이 안전한 이유는 두 가지다.

1. 보상 커맨드는 앞 단계가 없었어도 안전하다. inventory는 예약 없이 해제가 오면 "해제됨" 기록을, point는 사용 없이 환불이 오면 "환불됨" 기록을 남겨 늦게 온 예약·차감을 막고, 둘 다 항상 성공 응답을 보낸다
2. 같은 주문의 커맨드는 키가 같아 **보낸 순서대로** 처리된다(ADR 0005). 참여 서비스가 나중에 살아나도 밀린 `UsePoint`가 먼저, `RefundPoint`가 나중에 처리되어 결과는 "차감 후 환불"이다 (시나리오 4b)

포기한 뒤 늦게 온 성공 응답(`PointUsed`, `StockReserved`)은 현재 단계가 기다리는 응답이 아니라 무시한다. 단계가 되돌아가지 않는다.

### 결제는 포기하지 않는다

결제는 "응답 없음"이 "돈이 안 나갔음"을 뜻하지 않는다. PG가 승인했는데 결제 서비스가 기록 전에 죽었거나, PG 응답이 늦을 수 있다. 여기서 포기하고 보상하면 **돈은 나갔는데 주문은 취소**된다. 그래서 `PAYING`에서는 `Pay`를 계속 다시 보낸다. 결제 서비스는 같은 주문의 `Pay`에 기록된 결과를 다시 응답하고, PG는 `orderId`로 멱등이라 두 번 승인하지 않는다.

결제 서비스 안에서 PG 타임아웃(결과 모름)을 PG 조회로 확정하는 것, 결제 단계도 일정 시간 뒤 포기하되 늦게 승인되면 자동 환불하는 것은 3-D-2에서 다룬다(결제 취소 커맨드 추가).

### 보상은 끝까지 다시 보낸다

보상을 포기하면 재고·포인트가 묶인 채 남는다. 보상 커맨드는 멱등이라 몇 번 보내도 안전하므로 성공할 때까지 `step-timeout` 간격으로 다시 보낸다. 재전송 횟수가 `max-resends`를 넘으면 경고 로그를 남긴다(경보는 후속 관측성 작업).

### 동시성

- 응답 처리와 타임아웃 처리는 같은 Saga 행 락(`SELECT … FOR UPDATE`)을 잡는다. 겹쳐도 하나씩 처리된다
- 스캔은 잠그지 않고 id만 읽는다. Saga마다 따로 트랜잭션에서 잠근 뒤 `updatedAt`으로 **다시 판단**한다. 그사이 응답이 와서 진행됐거나 다른 인스턴스가 방금 재전송했으면 아무것도 하지 않는다. 그래서 order-service를 여러 개 띄워도 같은 Saga를 두 번 처리하지 않는다
- Saga 변경 + 재전송 커맨드 outbox 저장 = 한 트랜잭션 (원자성은 응답 처리와 같음)
- 스캔 쿼리는 진행 중 Saga만 담은 부분 인덱스(`idx_order_sagas_in_progress_updated_at`)를 쓴다. 끝난 Saga는 계속 쌓이므로 인덱스에서 뺐다

### 값 정하기

- `step-timeout`은 정상 응답 시간(수백 ms ~ 1초, 시나리오 7)보다 충분히 길어야 한다. 짧으면 정상 Saga에 불필요한 재전송이 나간다(결과는 같지만 부하)
- `step-timeout × (max-resends + 1)`은 **참여 서비스가 죽었다 살아나는 시간보다 길어야** 한다. 짧으면 복구될 장애도 보상으로 끝난다. 프로세스가 죽으면 Kafka가 그 컨슈머를 `session.timeout.ms`(기본 45초) 뒤에야 그룹에서 빼므로, 재기동 시간 + 45초가 하한이다 (시나리오 4에서 발견). 기본값 30초 × 4 = 2분
- 단계마다 다르게 둘 수도 있지만(결제는 더 길게 등) 지금은 하나로 둔다

## 대안

- **Saga마다 데드라인 시각을 저장**(`deadline_at`): 단계마다 다른 시간을 두기 쉽다. 지금은 `updatedAt` + 공통 타임아웃으로 충분하고 컬럼·인덱스가 하나 덜 든다
- **지연 메시지(타이머 토픽)로 타임아웃 이벤트 예약**: 스캔이 없지만, Kafka에는 지연 전달이 없어 별도 토픽·소비자가 필요하고 같은 주문의 순서 보장과 섞인다(ADR 0012에서 retry 토픽을 안 쓴 이유와 같음)
- **재전송 없이 바로 보상**: 일시적인 응답 유실(DLT)에도 주문이 취소된다. 재전송은 멱등이라 비용이 거의 없다
- **워크플로 엔진(Temporal 등)의 타이머**: 3-E ADR 0000에서 비교한다

## 결과

- 좋은 점: 응답이 오지 않아도 Saga가 끝난다(완료 또는 취소). 일시 장애는 재전송으로 이어서 완료, 긴 장애는 역순 보상으로 재고·포인트가 풀린다. 결제는 애매한 상태에서 섣불리 보상하지 않는다
- 비용: order-service가 주기적으로 진행 중 Saga를 조회한다(기본 5초에 한 번, 인덱스 조회). 재전송만큼 참여 서비스가 중복 응답을 보낸다
- 한계: 결제 서비스가 오래 다운되면 Saga는 `PAYING`에서 계속 기다린다(재고·포인트가 그동안 묶임). 3-D-2에서 결제 포기 + 늦은 승인 자동 환불로 푼다
