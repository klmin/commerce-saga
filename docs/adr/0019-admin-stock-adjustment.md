# ADR 0019. 관리자 재고 조정: inventory 관리자 API 로 입고·차감 (증감 + 이력 + 요청 키)

- 상태: 채택
- 날짜: 2026-11-27

## 배경

상품은 product-service 가, 재고는 inventory-service 가 주인이다. 재고 행은 시드(상품 5개)로만 만들어졌고 재고를 넣는 API 가 없었다.
그래서 관리자가 화면에서 새로 등록한 상품은 inventory 에 재고 행이 없어, 주문하면 늘 재고 예약 실패 → 주문 취소로 끝났다
(PROGRESS 5절 "알려진 한계"). 브리프의 ADMIN 역할에도 "상품·재고 관리"가 있다.

정할 것:

1. 재고 행을 누가 언제 만드는가 (상품 등록 이벤트로 자동 vs 관리자가 입고할 때)
2. 수량을 어떻게 바꾸는가 (값을 덮어쓰기 vs 더하고 빼기)
3. 관리자가 두 번 누르거나, 응답을 못 받고 다시 보낼 때
4. inventory 가 상품이 있는지 확인하는가

## 결정

1. **관리자 API 는 inventory-service 에 둔다**: `POST /admin/stocks/{productId}/adjustments`, `GET /admin/stocks/{productId}/adjustments` (ADMIN, Gateway `/api/admin/stocks/**`).
   - 재고 행은 **처음 입고할 때** 0 으로 만들고 조정한다(`insert … on conflict do nothing` → 행 락).
   - 상품 등록 이벤트로 재고 행을 만들지 않는다. product-service 는 메시지를 발행하지 않고(ADR 0010), 행만 미리 만들어 두어도 0 이라 주문 결과는 같다. 메시지 계약을 늘릴 이유가 없다.
2. **수량은 증감(delta)으로 바꾼다**: 입고는 양수, 차감은 음수.
   - 주문 예약과 같은 행 락(`SELECT … FOR UPDATE`) 안에서 가용 재고(`available`)에 더한다. 값을 덮어쓰면, 관리자가 화면을 읽은 뒤 들어온 예약분을 지운다(lost update).
   - 예약 중 수량(`reserved`)은 건드리지 않는다. 가용보다 많이 빼면 409 이고 아무것도 바꾸지 않는다.
   - 한 번에 ±1,000,000, 사유는 200자까지다.
3. **`Idempotency-Key` 필수**: 관리자 화면이 조정 한 번마다 UUID 를 만들고, 성공하면 새 키로 바꾼다.
   - `stock_adjustments` 의 `(adjusted_by, idempotency_key)` 유니크로 막는다.
   - 같은 키에 같은 내용(상품·수량·사유)이면 다시 반영하지 않고 처음 기록을 200 + `Idempotent-Replayed: true` 로 돌려준다. 내용이 다르면 422 다.
   - 키는 행 락 뒤에 확인한다. 그래서 같은 키로 동시에 와도, 뒤 요청은 앞이 커밋한 기록을 보고 다시 반영하지 않는다(통합 테스트).
   - 주문 `Idempotency-Key` 는 선택(7일 보관)이다. 재고 조정은 중복 반영이 곧 재고 불일치라 필수로 두고, 기록이 이력이라 지우지 않는다.
4. **이력은 `stock_adjustments` 에 남긴다** (추가 전용, bigint IDENTITY, ADR 0018 의 "내부 추가 전용 로그").
   - 누가(토큰 `sub`)·언제·얼마나·조정 뒤 가용·사유를 남긴다.
   - 재고 변경과 한 트랜잭션이다. 다른 서비스에 알릴 일이 없어 outbox 메시지는 없다.
5. **상품이 있는지 확인하지 않는다**.
   - inventory 는 상품 목록을 갖고 있지 않다. 확인하려면 product 동기 조회(ADR 0016 같은 예외)나 상품 읽기 모델이 필요한데, 얻는 것이 작다.
   - 없는 상품 id 의 재고는 주문될 일이 없어 무해하다. 화면은 상품 관리 화면에서만 이 API 를 부른다.

## 결과

- 관리자가 등록한 상품도 입고하면 주문할 수 있다. 관리자 상품 화면에 재고 카드(지금 재고·조정 폼·최근 20건 이력)를 붙였다.
- 입고와 예약이 동시에 와도 둘 다 반영된다(행 락 직렬화, `AdminStockIntegrationTest`).
- 사용자 화면의 재고 표시(`GET /stocks/{id}`)는 그대로다. 재고 행이 없으면 404 → "확인 불가"다.
- 재고 조정 사유를 표준 코드(입고·파손·실사 등)로 나누지 않았다. 필요해지면 열을 추가한다.
- 관리자 조정은 시스템 밖 입력이라 outbox 이벤트(`StockAdjusted`)를 내지 않는다. 재고 변동을 구독할 소비자(예: 품절 알림)가 생기면 그때 이벤트를 추가한다.
