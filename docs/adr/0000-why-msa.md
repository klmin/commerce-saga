# ADR 0000. 왜 MSA인가: 이 규모는 모놀리스로 충분하지만, 분산 정합성을 검증하려고 나눴다

- 상태: 채택
- 날짜: 2026-11-23

## 배경

주문·재고·포인트·결제를 다루는 쇼핑몰은 이 정도 규모(서비스 5개, 개발자 한 명, 트래픽 없음)라면 **모놀리스 하나로 충분하다.** DB 하나에서 주문·재고 차감·포인트 차감·결제 기록을 한 트랜잭션으로 묶으면 이 저장소가 푸는 문제의 대부분이 처음부터 생기지 않는다.

| | 모놀리스 (DB 하나) | 이 저장소 (서비스·DB 분리) |
|---|---|---|
| 주문 + 재고 + 포인트 | 로컬 트랜잭션 하나, 실패하면 롤백 | Saga + 역순 보상 |
| 변경 + 메시지 발행 | 필요 없음 (같은 트랜잭션) | Transactional Outbox + relay |
| 중복 전달 | 없음 | 멱등 컨슈머 두 겹 |
| 참여자가 응답 안 함 | 없음 | 단계 타임아웃·재전송·포기 후 보상 |
| 운영 대상 | 앱 1, DB 1 | 앱 5, DB 5(논리), Kafka, Kafka Connect |

실제 서비스였다면 모듈 경계를 잘 나눈 모놀리스(모듈러 모놀리스)로 시작하고, 팀이 늘거나 배포·확장 요구가 서비스마다 갈릴 때 나누는 것이 맞다.

## 결정

**그래도 서비스와 DB를 나눈다.** 이 프로젝트의 목적은 커머스 기능이 아니라 **분산 정합성 문제를 직접 재현하고 해결해 증명하는 것**이기 때문이다. 나누지 않으면 증명할 문제가 없다.

- 나눈 뒤 생기는 문제를 숨기지 않고 시나리오로 재현한다: 결제 실패 보상(1), 결제 타임아웃(2), 중복 전달(3), 참여 서비스 다운(4), relay 중단(5), 처리 불가 메시지(6), 알림 장애 격리(8)
- 경계는 진짜 MSA처럼 지킨다: 서비스마다 DB·계정, 서비스 간 HTTP 호출 없음, 공유 모듈은 메시지 스키마와 outbox 인프라뿐 (ADR 0001, AGENTS.md)
- 서비스를 나누는 기준은 트랜잭션 경계다. 재고·포인트·결제는 각자 자기 데이터의 정합성을 책임지고, 주문은 그 셋을 묶는 흐름만 책임진다

### 메인 Saga 방식: 대안 비교

서비스를 나눈 뒤 "주문 하나가 세 서비스에 걸치는 흐름"을 어떻게 돌릴지도 대안이 있다. 오케스트레이션 vs 코레오그래피 비교는 ADR 0003에 있고, 여기서는 그 밖의 대안까지 넓혀 왜 **Kafka 커맨드/응답 오케스트레이션**인지 적는다.

| | ① 동기 API 오케스트레이션 + 이벤트 뒷처리 + 대사 배치 | ② 워크플로 엔진 (Temporal 등) | ③ 순수 코레오그래피 | **이 저장소: Kafka 커맨드/응답 오케스트레이션** |
|---|---|---|---|---|
| 흐름 | 주문 서비스가 재고·포인트·결제 API를 차례로 호출 | 엔진의 워크플로 코드가 activity를 호출 | 각 서비스가 앞 서비스의 이벤트를 듣고 다음 일을 함 | order-service 상태 머신이 커맨드를 보내고 응답을 받음 |
| 상태·재시도·타임아웃 | 호출 코드 + 실패 시 대사 배치로 사후 보정 | 엔진이 맡음 (이벤트 히스토리, 재시도 정책, 타이머) | 서비스마다 흩어짐 | Saga 행(DB) + outbox + 단계 타임아웃을 직접 구현 |
| 참여 서비스 장애 | **곧 주문 장애** (호출이 실패·지연) | 엔진이 재시도하며 기다림 | 메시지가 쌓였다가 복구 후 처리 | 메시지가 쌓였다가 복구 후 처리, 오래 걸리면 포기 후 보상 (시나리오 4) |
| 보상 순서 | 호출 코드의 catch, 놓치면 대사 배치 | 워크플로 코드 (Saga 헬퍼) | 관리하기 어려움 (누가 무엇을 되돌릴지가 흩어짐) | 상태 머신 한 곳, 전이 표를 단위 테스트 |
| 운영 인프라 | 가장 적음 | 엔진 클러스터(+ 저장소) 추가 | Kafka | Kafka (+ Debezium) |
| 실무에서 | 가장 흔함 | 늘어나는 중 | 단순한 흐름에서 | 흔함 |

- **①을 택하지 않은 이유**: 실무에서 가장 흔하고 단순하지만, 참여 서비스가 느리거나 죽으면 주문 API가 같이 느려지고 실패한다. 서비스를 나눈 이점(장애 격리)이 주문 흐름에서는 사라진다. 정합성은 대사 배치가 나중에 맞추므로 "언제, 무엇이 어긋났는지"가 이 저장소에서 보이려는 메커니즘 밖으로 나간다
- **②를 택하지 않은 이유**: 실제 서비스라면 가장 먼저 검토할 만하다. Saga 상태 저장·재시도·타임아웃·보상을 엔진이 맡고 Kafka는 이벤트용으로 남는다. 하지만 이 프로젝트가 증명하려는 메커니즘(상태 저장, 원자적 발행, 멱등, 타임아웃 후 보상)이 엔진 뒤로 숨고, 운영 인프라가 하나 더 늘어난다
- **③을 택하지 않은 이유**: 단계가 넷이고 보상 순서(결제 취소 → 포인트 환불 → 재고 해제)가 중요하다. 흐름이 서비스마다 흩어지면 순서와 "지금 어디까지 왔나"를 한 곳에서 답할 수 없다. 대신 후속 처리(판매 확정·알림)는 코레오그래피로 둔다 (ADR 0003)
- **결론**: 메커니즘을 직접 구현하고 시나리오로 증명하려는 목적, 그리고 참여 서비스 장애가 주문 API로 번지지 않는 장애 격리 때문에 Kafka 커맨드/응답 오케스트레이션을 택한다

## 결과

- 좋은 점: 분산 정합성 문제(이중 쓰기, 중복 전달, 늦은 응답, 응답 없음, 결과를 모르는 결제)를 실제로 만나고, 코드·테스트·시나리오로 해결을 보인다
- 나쁜 점: 이 규모에 비해 운영 부품이 많다(서비스 5, Kafka, Kafka Connect). 로컬 실행·CI가 무겁다(e2e가 relay 모드마다 7~10분). 주문은 비동기라 API가 바로 결과를 주지 못하고 `PENDING`을 돌려준다
- 이 ADR은 나중에 쓴 것이다. 이미 머지된 ADR 0003은 고치지 않고, 대안 비교는 여기에 둔다
