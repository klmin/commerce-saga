# ADR 0003. 메인 주문 Saga는 오케스트레이션, 후속 처리는 코레오그래피

- 상태: 채택
- 날짜: 2026-11-22

## 배경

주문 하나가 재고 예약 → 포인트 차감 → 결제 세 서비스에 걸치고, 어느 단계든 실패하면 이미 성공한 앞 단계를 되돌려야 한다. 서비스마다 DB가 따로라 분산 트랜잭션(2PC)은 쓰지 않는다(ADR 0001). 남은 선택지는 Saga이고, 구현 방식이 둘이다.

| | 오케스트레이션 | 코레오그래피 |
|---|---|---|
| 흐름을 아는 곳 | 오케스트레이터 한 곳 (상태 머신) | 각 서비스가 이벤트를 보고 스스로 판단 |
| 메시지 | 커맨드(`ReserveStock`) + 응답 | 이벤트(`OrderCreated`, `StockReserved` ...) |
| 보상 순서 | 상태 머신이 역순으로 지시 | 각 서비스가 실패 이벤트를 듣고 각자 되돌림 |
| 진행 상태 조회 | 오케스트레이터 DB 한 곳 | 여러 서비스 로그를 모아야 함 |
| 결합 | 오케스트레이터가 참여자 커맨드를 앎 | 서로의 이벤트를 앎 (흐름이 코드에 흩어짐) |

## 결정

- **메인 주문 Saga = 오케스트레이션.** order-service가 `OrderSaga` 상태 머신을 DB에 저장하고 단계별 커맨드를 보낸다.
  - 단계가 4개(재고·포인트·결제·완료)이고 보상 순서(포인트 환불 → 재고 해제)가 중요하다. 순서를 한 곳에서 정하고 테스트할 수 있어야 한다 (`OrderSagaTest`가 전이 표 전체를 검증).
  - "이 주문이 지금 어디까지 왔나"를 한 행으로 답할 수 있다 → Saga 상태 조회(`GET /orders/{id}/saga`, 본인 주문만. 관리자 전체 화면은 4단계), 3단계 타임아웃 감시.
- **후속 처리 = 코레오그래피.** 주문 결과는 `order.events`(`OrderCompleted`, `OrderCancelled`)로 알리고, 받는 쪽은 order-service가 모른다.
  - inventory: `OrderCompleted` → 예약 재고 판매 확정
  - notification: 사용자 알림
  - 이후 정산·통계도 order-service 수정 없이 소비자만 추가
  - 이 처리들은 주문 성공 여부에 영향이 없다. 알림이 죽어도 주문은 완료된다 (시나리오 8)

### 상태 머신 설계

```
정방향: RESERVING_STOCK -> USING_POINT -> PAYING -> COMPLETED
보상:   (실패) -> REFUNDING_POINT -> RELEASING_STOCK -> CANCELLED
```

- 도메인(`OrderSaga.handle`)은 응답 하나를 받아 "다음에 할 일"(`SagaAction`)만 돌려준다. 메시지 발행·주문 상태 반영은 애플리케이션이 한다. 도메인이 Kafka를 모르므로 순수 단위 테스트로 전이를 검증한다.
- **현재 단계에서 기다리는 응답이 아니면 무시한다.** at-least-once 전달이라 중복·늦은 응답이 온다. 예: 결제 실패로 보상 중인데 늦게 온 `PaymentApproved` → 무시. 단계가 되돌아가거나 커맨드가 두 번 나가지 않는다.
- 보상 커맨드(`RefundPoint`, `ReleaseStock`)는 참여자 쪽에서 "여러 번 와도, 앞 단계가 없었어도 안전하고 항상 같은 응답"을 계약으로 정했다. 오케스트레이터가 보상을 재전송해도 이중 환불·이중 해제가 없다.
- 응답은 세 토픽(`inventory/point/payment.reply`)의 서로 다른 리스너로 온다. 같은 주문의 응답 처리는 Saga 행 `SELECT ... FOR UPDATE`로 줄 세운다.

### 타협: Order와 OrderSaga를 한 트랜잭션에서 바꾼다

Saga가 끝나는 응답을 처리할 때 한 트랜잭션에서 `OrderSaga` 전이, 다음 커맨드·이벤트 outbox 저장, `Order` 상태(COMPLETED/CANCELLED) 반영을 함께 한다. "한 트랜잭션 = 애그리거트 하나"의 예외다. 같은 서비스·같은 DB 안이고, 둘을 나누면 "Saga는 끝났는데 주문은 PENDING" 같은 상태를 다시 맞추는 장치가 필요해서 로컬 트랜잭션으로 묶었다.

## 결과

- 좋은 점: 흐름과 보상 순서가 `OrderSaga` 한 클래스에 있다. 진행 상태와 타임라인을 바로 조회한다. 후속 소비자는 자유롭게 늘린다.
- 나쁜 점: order-service가 참여 서비스의 커맨드 계약을 안다(오케스트레이터 결합). 단계가 늘면 상태 머신이 커진다.
- 남은 일(3단계): 응답이 오지 않는 단계의 타임아웃·재시도, 결과가 애매한 결제 타임아웃의 조회 후 보정(ADR 0007).
- 여유가 생기면 같은 흐름을 코레오그래피로 구현한 브랜치를 두고 이 ADR에 비교를 덧붙인다.
