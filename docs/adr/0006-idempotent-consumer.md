# ADR 0006. 멱등 컨슈머: 메시지 ID 기록(processed_message) + 주문별 기록, 두 겹

- 상태: 채택
- 날짜: 2026-11-22

## 배경

전달은 at-least-once다. 같은 메시지가 다시 오는 경로가 여럿 있다.

| 경로 | 다시 오는 것 |
|---|---|
| relay가 Kafka에 보내고 ack를 받았는데 outbox 행을 지우기 전에 죽음 | **같은 메시지**(같은 `id`)를 다시 발행 |
| 컨슈머가 처리·커밋했는데 오프셋을 커밋하기 전에 죽음 / 리밸런스 | **같은 메시지**를 다시 받음 |
| 운영자가 장애 복구 중 오프셋을 되감음 (시나리오 3) | **같은 메시지** 여러 건을 다시 받음 |
| 오케스트레이터가 응답을 못 받아 커맨드를 다시 보냄 (3-D 타임아웃 재시도) | **내용은 같고 ID가 다른** 메시지 |

2단계까지는 주문별 기록(재고 예약·포인트 사용·결제 기록, `order_id` 유니크)으로 중복을 걸렀다. 상태가 두 번 바뀌지는 않지만, 다시 온 메시지마다 응답을 다시 보냈다. 오프셋을 되감으면 응답이 그만큼 또 쌓이고, 오케스트레이터는 그걸 다 받아 상태 머신으로 버려야 했다.

## 결정

### 두 겹으로 거른다

1. **메시지 ID (`processed_message`)**: 같은 메시지의 재전달을 거른다. 상태도, 응답도 바꾸지 않고 건너뛴다
2. **주문별 기록 (기존)**: 내용이 같은 다른 메시지를 거른다. 상태는 그대로 두고 **처음 결과를 다시 응답**한다 (오케스트레이터의 재요청에는 답해야 하므로)

1만 있으면 오케스트레이터가 재요청할 때(새 ID) 재고를 다시 잡는다. 2만 있으면 재전달마다 응답이 다시 나간다. 그래서 둘 다 둔다.

### 구현

- 메시지 ID = Kafka 헤더 `id` = 보낸 쪽 outbox 행의 `id`. Debezium Outbox Event Router도 outbox `id`를 같은 헤더로 내보내므로, relay를 Debezium으로 바꿔도 컨슈머는 그대로다 (ADR 0005)
- 서비스마다 자기 DB에 `processed_message(message_id uuid pk, processed_at)`
- 상태를 바꾸는 유스케이스는 `(messageId, 커맨드)`를 받고, **트랜잭션 첫 줄에서** `insert ... on conflict do nothing`. 1건이면 처리, 0건이면 건너뛴다
  - 비즈니스 변경, outbox 응답, `processed_message`가 한 트랜잭션이다. 처리 중 실패해 롤백되면 기록도 사라져 재시도 때 다시 처리된다
  - 같은 메시지가 동시에 두 번 처리되면(리밸런스 직후 등) 늦은 쪽 INSERT가 앞쪽 커밋을 기다렸다가 0건이 되어 건너뛴다
  - 기록 어댑터는 `@Transactional(MANDATORY)`라 트랜잭션 밖에서 부르면 바로 오류가 난다
- `id` 헤더가 없거나 UUID가 아니면 멱등 처리를 할 수 없으므로 재시도 불가 오류로 DLT에 보존한다
- 위치: `application/port/out/ProcessedMessagePort` + `adapter/out/persistence`. 판단(건너뛸지)은 애플리케이션 서비스가, 저장은 어댑터가 한다. 리스너에서 트랜잭션을 열어 감싸는 방식은 쓰지 않았다. payment는 PG 호출을 트랜잭션 밖에서 해야 해서(외부 호출 중 커넥션·락을 잡지 않으려고) 리스너 전체를 트랜잭션으로 감쌀 수 없기 때문이다

| 서비스 | 대상 | 비고 |
|---|---|---|
| inventory | `ReserveStock`, `ReleaseStock`, `OrderCompleted`(판매 확정) | 관심 없는 이벤트 타입은 기록 없이 건너뜀 |
| point | `UsePoint`, `RefundPoint` | |
| payment | `Pay` | PG 호출 전에 읽기로 한 번 확인(재전달이면 PG도 안 부름), 최종 판단은 기록 트랜잭션의 INSERT |
| order | 세 응답 토픽 | 그 뒤 상태 머신이 중복·늦은 응답을 한 번 더 거른다 (ADR 0003) |
| notification | 적용 안 함 | 알림은 `(order_id, type)` 유니크 하나로 충분. 응답을 보내지 않아 재전달 비용이 없다 |

### 보존 기간

`processed_message`는 계속 쌓인다. 행을 지워도 되는 시점은 "그 메시지가 다시 올 수 없을 때"이므로, 보존 기간은 **토픽 보존 기간 + DLT 재처리 기간**보다 길어야 한다. `processed_at` 인덱스를 미리 두었고, 정리 작업은 운영 단계에서 붙인다. 지운 뒤에 아주 오래된 메시지가 다시 와도 2번째 겹(주문별 기록)이 상태 중복은 막는다.

## 결과

- 좋은 점: 오프셋을 되감아 전부 다시 받아도 재고·포인트·결제는 물론 응답·이벤트도 새로 나가지 않는다 (시나리오 3, CI `e2e`에서 토픽 끝 오프셋까지 비교)
- 좋은 점: 메시지 ID와 Debezium 헤더를 맞춰 두어 relay 교체(3-C)에 컨슈머 변경이 없다
- 비용: 메시지마다 INSERT 한 번. 같은 트랜잭션이라 왕복 한 번이 늘 뿐이다
- 주의 (배포 경계): 이 기록이 생기기 전에 처리한 메시지는 ID가 없다. 그 범위까지 되감으면 2번째 겹으로만 걸러져 상태는 그대로지만 응답은 다시 나간다(오케스트레이터가 무시). 로컬에서 실제로 확인했다
- 주의: 메시지 ID는 보낸 쪽이 정한다. 보낸 쪽이 같은 내용을 새 ID로 다시 보내는 것은 의도된 재요청으로 보고 2번째 겹에 맡긴다
