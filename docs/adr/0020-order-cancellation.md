# ADR 0020. 주문 취소: 진행 중이면 다음 응답에서 보상으로, 완료 후면 같은 Saga 의 취소 단계로

- 상태: 채택 (8-0)
- 날짜: 2026-11-28

## 배경

주문은 Saga 가 끝나야 결과(완료·취소)가 나고, 사용자가 주문을 취소할 방법이 없다 (PROGRESS 4-4절 "정하고 미룬 것", 5절 "주문 취소 API 없음").
4-4절에서 방향은 정해 두었다.

- Saga 진행 중 취소: 취소 요청을 기록하고, 다음 응답에서 보상으로 돌린다
- 완료된 주문 취소: 결제 환불 → 포인트 환불 → 재고 복구 순서의 취소 Saga

이 ADR 은 그 방향을 지금 구조(주문당 Saga 하나, 오케스트레이션, 단계별 타임아웃, 보상 커맨드는 여러 번 와도 안전)에 맞춰 구체화한다.

지금 구조에서 확인한 것:

- 결제 취소(`CancelPayment`)는 결제가 승인됐으면 결제 서비스가 환불까지 책임진다(늦은 승인 환불과 같은 경로, ADR 0007). 완료된 주문에도 그대로 쓸 수 있다
- 포인트 환불(`RefundPoint`)은 차감 기록을 되돌리고, 기록이 없거나 이미 환불했어도 안전하다. 그대로 쓴다
- 재고는 다르다. 주문이 완료되면 inventory 가 `OrderCompleted`(코레오그래피)로 예약분을 **판매 확정**한다(`CONFIRMED`, reserved 에서 빠짐). 지금 `ReleaseStock` 은 `RESERVED` 일 때만 예약을 풀고, 확정된 예약은 "되돌릴 것 없음"으로 응답한다. 완료 후 취소에는 **팔린 수량을 가용 재고로 다시 들이는** 동작이 필요하다

## 결정

### 1. 취소는 같은 Saga 의 단계로 처리한다 (취소 Saga 를 따로 두지 않는다)

주문당 Saga 하나(`order_sagas`, orderId 키)를 유지한다. 취소 요청은 Saga 에 기록되고, 이후는 지금의 보상 단계(`CANCELLING_PAYMENT` → `REFUNDING_POINT` → 재고)로 흐른다.
한 주문의 단계·이력·타임아웃이 한 곳에 있어 화면 타임라인, 단계 타임아웃 재전송, 늦은 응답 무시가 그대로 맞는다.

### 2. 진행 중 취소: 요청만 기록하고 다음 응답에서 보상으로

`cancelRequested` 를 Saga 에 남긴다. 진행 중인 단계의 커맨드는 이미 나갔으므로 끊지 않고, 그 응답이 왔을 때 정한다.

| 지금 단계 | 응답 | 취소 요청이 있으면 |
|---|---|---|
| 재고 예약 | 예약됨 | 다음 단계로 가지 않고 재고 해제 → 취소 |
| 재고 예약 | 실패 | 원래대로 취소 (보상 없음) |
| 포인트 차감 | 차감됨 | 포인트 환불 → 재고 해제 → 취소 |
| 포인트 차감 | 실패 | 원래대로 보상 |
| 결제 | 승인 | 결제 취소(환불) → 포인트 환불 → 재고 해제 → 취소 |
| 결제 | 실패 | 원래대로 보상 |
| 보상 중 | - | 이미 취소로 가는 중. 요청만 받아 둔다 |

결제 단계에서 바로 보상하지 않고 응답을 기다리는 것은 ADR 0007 과 같은 이유다(승인됐을 수 있다). 타임아웃 규칙은 그대로다(재전송 → 포기 시 보상).
취소 사유는 실패 사유와 구분해 "사용자 취소"로 남긴다.

### 3. 완료 후 취소: 결제 취소(환불) → 포인트 환불 → 재고 반환

`COMPLETED` 인 Saga 에 취소를 요청하면 `CANCELLING_PAYMENT` 부터 시작한다(결제 금액이 0 이면 건너뛰고, 포인트를 쓰지 않았으면 포인트 환불도 건너뛴다).
마지막 재고 단계는 새 단계 `RETURNING_STOCK` 과 새 커맨드 `ReturnStock` 이다.

- **`ReturnStock`(inventory.command) / `StockReturned`(inventory.reply)를 새로 만든다.** `ReleaseStock` 의 의미("잡은 예약을 푼다")를 "팔린 것도 다시 들인다"로 넓히지 않는다(메시지 계약은 의미를 바꾸지 않고 새 타입으로, ADR 0005)
- inventory 처리는 예약 상태에 따라 다르다
  - `CONFIRMED`: 확정분을 가용으로 다시 들인다(available += 수량). 새 상태 `RETURNED`
  - `RESERVED`: 아직 `OrderCompleted` 를 처리하지 않은 경우(이벤트가 늦음). 예약을 풀어 가용으로 돌리고(release 와 같음) `RETURNED`. 뒤늦게 온 `OrderCompleted` 는 `RESERVED` 가 아니므로 아무것도 하지 않는다(지금 `confirm` 규칙 그대로)
  - `RETURNED`·`RELEASED`·기록 없음: 되돌릴 것 없음. 그래도 항상 `StockReturned` 로 응답한다(보상 커맨드 규칙)
- 재고 반환은 관리자 입고(ADR 0019)와 같은 행 락 안에서 더한다. 반환은 보상이라 거절하지 않는다. 반환되는 판매 확정분은 관리자 입고 상한(가용 + 예약)에 세지 않는 수량이라 반환이 쌓이면 int 를 넘을 수 있으므로 재고 수량을 bigint 로 넓힌다(inventory V7)

### 4. 주문 상태와 이벤트

- 주문 상태는 그대로 `PENDING`/`COMPLETED`/`CANCELLED` 다. 취소가 끝나면 `CANCELLED`(완료됐던 주문도). 진행 중에는 응답에 `cancelRequested: true` 를 더한다
- 취소가 끝나면 지금처럼 `OrderCancelled` 를 낸다. 완료 후 취소인지 알 수 있게 필드 `afterCompletion` 을 **추가**한다(필드 추가만, ADR 0005). 옛 메시지에는 없으므로 `Boolean` 으로 받고 없으면 false 다(원시 boolean 이면 Jackson 3 기본 설정에서 옛 메시지를 읽지 못한다). 알림은 "주문이 취소되었습니다"로 같다

### 5. API·권한

- `POST /orders/{orderId}/cancel` (본인 주문만, 남의 주문은 404 — IDOR). 접수되면 202. 이미 취소 요청·취소된 주문에 다시 보내면 같은 결과(202·200)로 멱등
- 취소할 수 없는 경우는 없다(배송 단계가 없으므로 완료 후에도 기한 없이 취소). 부분 취소(줄 단위)는 하지 않는다
- 관리자 강제 취소는 이번 범위 밖이다(같은 Saga 경로를 관리자 API 에서 부르면 된다)

## 결과

- 사용자가 언제든 주문을 취소할 수 있고, 돈·포인트·재고가 정방향의 역순으로 되돌아간다
- 진행 중 취소는 바로 끝나지 않는다(진행 중인 단계의 응답을 기다린다). 화면은 "취소 요청됨"과 타임라인으로 보여 준다
- 완료 후 재고 반환은 팔린 상품이 그대로 다시 팔 수 있다고 본다(반품 검수 없음)
- 재고 반환과 뒤늦은 판매 확정이 엇갈려도 재고가 두 번 늘거나 음수가 되지 않는다(예약 상태로 판단)
