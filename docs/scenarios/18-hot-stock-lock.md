# 시나리오 18. 인기 상품 재고 락: 한 행에 몰린 예약의 처리량과 락 대기

재고 예약은 상품의 재고 행을 비관적 락(`SELECT … FOR UPDATE`, productId 순서)으로 잡는다. 정합성은 문제가 없지만, 한정 판매처럼 **한 상품에 주문이 몰리면** 그 행 하나에서 줄을 서서 처리량이 막힐 수 있다. 실제로 얼마나 막히는지 재 보고 락 방식을 바꿀지 정한다(PROGRESS 4-4절 "정하고 미룬 것"). 검증(PASS/FAIL)이 아니라 측정이다.

## 재현

1. 인프라(postgres, kafka)와 inventory-service 를 띄운다
2. `scripts/measure-hot-stock.sh` (기본: 커맨드 3000건, 상품 9001 하나)
   - `ReserveStock` 커맨드를 `inventory.command` 에 한꺼번에 넣는다. 오케스트레이터·HTTP 를 빼고 **재고 단계만** 본다(키 = orderId, 헤더 `id`·`type`). 응답은 order-service 가 "Saga 없는 주문의 응답"으로 무시한다
   - **처리량**: 예약 기록 `stock_reservations.created_at`(서버 시각)의 처음~끝 구간으로 나눈 건/초. 커맨드 발행(약 2초)이 처리보다 훨씬 빨라서 리스너 쪽 한계를 잰다
   - **리스너 한 건 처리 시간**: `/actuator/prometheus` 의 `spring_kafka_listener` 타이머 측정 전후 차이의 평균. 인스턴스가 여럿이면 합친다(`INVENTORY_URLS`)
   - **락 대기**: 처리하는 동안 한 연결에서 0.05초마다 `pg_stat_activity` 를 훑어, 재고 DB 에서 락(`wait_event_type = Lock`)을 기다리는 연결 수를 센다
   - 측정용 상품 9001~ 은 재고 행이 없는 id 만 쓴다(시드 상품 1~5 처럼 이미 있으면 덮어쓰지 않고 중단). 재고를 넉넉히 넣었다가, 끝나면(실패해도) 이번 실행이 만든 재고 행과 예약·멱등 기록만 지운다
3. 비교: `PRODUCTS="9001 9002 9003"`(세 상품에 고르게 = spread). 인스턴스 셋은 `SERVER_PORT` 만 바꿔 같은 컨슈머 그룹으로 두 개를 더 띄운다

## 병렬도의 상한

- 리스너는 인스턴스당 스레드 하나(`spring.kafka.listener.concurrency` 기본 1)이고, `inventory.command` 는 파티션 3개다
- 그래서 **한 재고 행을 동시에 잡으려는 트랜잭션은 많아야 3개**다. 인스턴스가 하나면 처리가 한 줄로 서므로 락 경합 자체가 없다
- HTTP 로 주문이 아무리 몰려도 재고 단계에 들어오는 동시성은 파티션 수가 정한다. 나머지는 Kafka 에 쌓여 기다린다(지연이 늘 뿐 DB 연결이 고갈되지 않는다)

## 결과 (로컬)

로컬(Windows, Docker Desktop, 서비스는 호스트 JVM, 워밍업 후), 커맨드 3000건, 2026-11-25:

| 인스턴스 | 상품 | 처리량 | 리스너 한 건 평균 | 락 대기 샘플 비율 (평균 대기 연결) |
|---|---|---|---|---|
| 1 | 1개 (hot) | 157 건/s | 6.3 ms | 0% |
| 1 | 3개 (spread) | 158 건/s | 6.3 ms | 0% |
| 3 | 1개 (hot) | **144 ~ 163 건/s** | 18 ~ 20 ms | **83 ~ 88%** (1.3 ~ 1.4) |
| 3 | 3개 (spread) | **258 건/s** | 10.9 ms | 33% (0.35) |

(인스턴스 3·hot 은 두 번 돌린 값. 두 번째 실행부터는 워밍업이 끝난 상태)

## 해석

- **인기 상품 하나의 상한은 약 150건/s**이고, 인스턴스를 늘려도 오르지 않는다. 늘어난 인스턴스는 그 행의 락을 기다릴 뿐이다. 리스너 한 건 시간이 6ms → 18~20ms 로 약 3배가 됐는데, 앞의 두 트랜잭션이 끝나기를 기다린 시간이다
- 상한은 **락을 쥐고 있는 시간**이 정한다. 지금은 `FOR UPDATE` 로 잡은 뒤 재고 갱신, 예약·예약 줄·outbox INSERT, 커밋(fsync)까지 쥐고 있어 한 건에 약 6ms → 1초에 약 160건
- 상품이 나뉘면 인스턴스 수만큼 늘어난다(158 → 258건/s). 상품 셋을 돌아가며 넣어 같은 상품끼리 부딪히는 경우가 남아 3배까지는 안 된다(락 대기 33%)
- 150건/s 는 한 상품에 분당 9,000건이다. 포트폴리오 규모와 시연 트래픽에는 충분하다. 포인트·결제 단계는 사용자·주문마다 다른 행이라 이 상한과 관계없다

## 결정

- **비관적 락을 유지한다.** 정합성이 명확하고, 이 규모에서는 한계에 닿지 않는다
- 인기 상품 처리량이 더 필요해지면 먼저 **락 쥐는 시간을 줄인다**: 조건부 UPDATE(`… set available = available - :n where product_id = ? and available >= :n`)를 트랜잭션 끝(INSERT 뒤, 커밋 직전)으로 옮기면 락은 UPDATE~커밋 동안만 잡힌다. 다만 커밋(fsync)은 그대로 락 안이라 얼마나 오르는지는 이 스크립트로 다시 재서 정한다
- 재고 버킷·Redis 선점은 상한을 근본적으로 올리지만, 버킷 사이 재분배나 Redis–DB 불일치 보정이라는 새 문제를 만든다. 측정상 필요가 없어 하지 않는다
- 인스턴스·파티션을 늘리는 것은 상품이 고르게 나뉜 트래픽에만 효과가 있다(인기 상품 하나에는 효과 없음)
